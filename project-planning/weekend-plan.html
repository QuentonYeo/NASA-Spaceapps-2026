Four parallel workstreams

1. Archive and fixtures

  1. In backend/notebooks/, query IRSA SIA2 for single exposures from spherex_dr1. Use spherex_qr3 when looking for newer observations. Save example metadata and record which fields carry IDs, dates and download URLs.
  2. Use IRSA MOST to locate exposures covering a known asteroid’s predicted positions. Download FITS cutouts centered on a common sky patch. Verify actual shared coverage, target visibility, comparable local wavelengths and distinct times.
  3. Write a small SPHEREx adapter in backend/app/services/ with search and cutout steps. Validate RA, Dec and FOV, enforce server-side limits on FOV and frame count, and cache by sky region, release and selection parameters. Make errors and partial coverage visible.

Handoff: reproducible fixture with source links and a cached demo selection. IRSA archive access · MOST

2. Image processing

All three tasks completed on the M101 sample.

  1. Mask pixels and estimate the local background

    Read brightness, quality flags, variance, and sky and wavelength coordinates from the FITS files. Masked documented bad-pixel flags, including OUTLIER, and rejected nonfinite brightness or invalid variance. The SOURCE flag covered over 99% of the small cutouts, so the background came from wider cutouts of the same exposures. For each, we took the 3-sigma-clipped median of usable, source-free pixels 6–8 arcminutes from M101.

    The first three exposures gave backgrounds of 0.196, 0.333, and 0.184 MJy/sr. Invalid and uncovered pixels kept separate mask codes. The May 14 frame left 1,548 pixels uncovered on the 59 × 59 grid. Background and mask report · Aligned frames

  2. Align frames and inspect signed differences

    Aligned four exposures to the May 10 celestial WCS with nearest-neighbor sampling. Compared all six pairs and required pixels to be valid in both exposures, with at least 80% overlap of the wider nominal wavelength band at that pixel.

    One pair qualified. May 16 (1.503 µm at M101) minus May 10 (1.506 µm) yielded 3,268 comparable pixels. Four reference-star candidates selected from the images showed centroid shifts of 0.12–0.39 pixels. The brightest left adjacent positive and negative residuals. Use this difference as a diagnostic. Refine the subpixel alignment and match stellar profiles before using residuals as detection evidence. Pair and star measurements · Residual inspection

  3. Export UI assets and preserve FITS provenance

    Exported both frames as 59 × 59 PNGs with a shared linear stretch of 0.205–2.571 MJy/sr. The signed overlay uses red for positive differences and blue for negative differences, with opacity based on magnitude and full transparency over masked pixels. All PNGs use the same top-left origin.

    The FITS products preserve calibrated pixel arrays, variance, and masks for analysis. The manifest and embedded provenance record the IRSA source URLs, FITS checksums, and coordinate mapping. May 10 preview · May 16 preview · Overlay · Difference FITS · UI manifest

3. Viewer and integration

  1. In frontend/, load the fixture on startup. Build RA, Dec and FOV inputs, play/pause, frame selection, zoom and contrast. Contrast applies across the sequence and zoom preserves the view when changing frames.
  2. Show time, local wavelength, release, loading and missing or partial coverage. Add frame selection for detection and toggleable difference, candidate and known-object overlays. Draw markers in processed frame coordinates and apply the same zoom transform as the image.
  3. Connect FastAPI live search with a visible path back to the demo. For known stars, use Gaia DR3 positions propagated to the frame epoch where proper motion is available. For the verified asteroid, use MOST predictions at each exposure time.

Handoff: a complete browser workflow exercised against the same manifest in cached and live modes. Gaia DR3

4. Candidate detection

  1. Start with a baseline. Find point-like peaks in cleaned images or difference overlays, then link plausible positions across selected frames. Score repeat detections, signal relative to noise, track consistency and distance from flagged pixels. Describe two-frame results as tentative.
  2. Return candidate ranks with frame IDs, marker positions and evidence. Validate against the held-out asteroid predictions after ranking. Record tolerances in pixels or angular distance and inspect the strongest artifacts.
  3. If there are enough labeled tracks, train a small classifier on the same features and compare with the baseline on a separate field. Report both ranks and false leads. Show users whether the active ranking is rules-based or learned.

Handoff: ranked candidates, evidence overlays and a short recovery report. Unmatched tracks remain candidates for review.

Shared contract for the first integration

Use the existing Python/FastAPI backend and React/TypeScript frontend. The backend handles archive queries, coordinates, processing and detection. The frontend renders aligned images and overlays. Start with a JSON fixture so both sides can work in parallel.

Sequence { id, centerRaDeg, centerDecDeg, fovDeg, grid, frames[] }
Grid     { width, height, orientation }
Frame    { id, observedAtUtc, release, detector, wavelengthUm,
           previewUrl, sourceFitsUrl, coverage, status }
Candidate { id, rank, score, method, reasons[], detections[] }
Detection { frameId, xPx, yPx, raDeg, decDeg }

Use UTC ISO timestamps, ICRS coordinates in degrees, and micrometres for wavelength. Store preview pixels with a top-left origin. Define wavelengthUm at the sequence center and label it as such. Use wavelength at the source position for candidate comparisons where available. Represent unknown values as null and give incomplete frames an explicit status. Keep raw FITS, variance and masks on the backend. Keep the asteroid prediction overlay available as a separate reveal.

Suggested routes. GET /api/demo serves the cached manifest. GET /api/frames takes RA, Dec and FOV and returns the same manifest shape. POST /api/detect takes a sequence ID and selected frame IDs and returns ranked candidates. A cached demo can ship with precomputed candidates if on-demand processing is still slow.

Scope decisions

Ship first

Time playback at comparable wavelengths, zoom and contrast, frame metadata, one aligned real sequence and a candidate reveal. Use live IRSA search for a bounded request. If live access fails during judging, use the cached sequence and show its provenance.

Add once the demo works

Try a wavelength navigator grouped into six detector bands, with gaps visibly disabled. For wavelength browsing, use DR1 All-Sky Cube channels or exposures from a chosen time window. Label a cube view as combined observations. For a spectrum, plot brightness against wavelength at a selected sky position using a cube or calibrated measurements across exposures.

Keep as stretch goals

Add shareable URL state for region, mode and selected frame, then document embedding. Use the sequence manifest as the boundary for another archive or a user-supplied overlay. Start with one documented import format and validate coordinates and units before adding plugins.

Defer molecular maps

Mapping methane, water or CO₂ requires validated spectral features, a continuum estimate and uncertainty checks. If you build the spectrum panel, use annotated feature wavelengths as an educational aid while the team evaluates whether the data support a map.
